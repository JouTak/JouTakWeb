# ADR 001: серверные сообщества и объединения игроков

Принято локально 21.09.2026 после получения обоих агентских документов.

## Основание и границы

Последнее уточнение охватывает официальные сообщества серверов и клубы, команды,
гильдии игроков. В проверенной demo DB одна Community (`itmocraft`), четыре
активных membership и три связанных City. Идентификаторы, связи, тексты и
настройки этих записей сохраняются. Другие окружения не классифицируются по имени.

Выбран отдельный Django app `playergroups`. Community/CommunityMembership
остаются серверным контекстом, PlayerGroup/GroupMembership — добровольным
объединением. Общий каталог `/communities` показывает обе категории. Это
устраняет необходимость менять каждый consumer существующего shared_communities:
новые группы вообще не входят в прежнюю аудиторию профиля и городские права.
Рекомендация первого документа ограничить каталог только клубами уступает
переданному во втором документе уточнению охвата пользователя.

## Модель и переходы

PlayerGroup: неизменяемые slug и optional scope Community, категория club/team/guild,
draft/active/archived, public/unlisted/private, open/approval/invite_only,
accepting/paused, public/members/private roster, версия содержимого, ограничение
платформой. Private требует invite_only. Unlisted доступна любому по ссылке и
не называется секретной. Описание — Markdown без raw HTML; контакты отдельно
public/members, проверенные Discord/Telegram/VK. Изображения используют уже
существующее хранилище и остаются публичными по URL.

Уникальная GroupMembership(user, group): active/left/removed, member/moderator/
manager, видимость public/members/private, даты текущего и первого вступления.
Новая связь private по умолчанию. Управленческий состав показывает минимальный
username, разрешённый Minecraft nick и роль; обычный состав — только разрешённые
идентичности. Обычный count означает «Открытые профили», управленческий — весь
действующий состав. Скрытый roster не возвращает общий total.

JoinRequest и Invitation хранят отдельные процессы, не pending membership.
Открытое вступление, одобрение заявки и принятие приглашения создают только member.
Повтор сохраняет joined_at, не множит membership/audit. Совпадающие pending-процессы
закрываются в той же транзакции. Истечение проверяется при каждом действии;
GET не изменяет БД. Пауза запрещает все новые вступления и принятия, но допускает
отказ/отзыв/выход. Архив закрывает pending; восстановление оставляет набор на паузе.

Приглашения и LeadershipOffer теряют силу при утрате отправителем текущих прав;
это выбранная из двух рекомендаций политика, без скрытого сохранения полномочий.
Назначение manager требует предложения действующему участнику и его согласия.
Передача повышает адресата и понижает отправителя атомарно. Created_by не даёт прав.
Удаление и запрет повторного вступления различаются; запрет не обходится rejoin.

## Права

| Действие | Member | Moderator | Manager | Platform moderator |
|---|---|---|---|---|
| Выйти / изменить свою видимость | Да | Да | С защитой последнего | Только своё |
| Описание / контакты / изображения | — | Да | Да | Да |
| Заявки / приглашения | — | Да | Да | Да |
| Удалить / ограничить обычного участника | — | Да | Да | Да |
| Роль moderator / доступ и набор | — | — | Да | Да |
| Предложить управление | — | — | Да | Да |
| Снять чужого manager | — | — | — | С причиной |
| Архив / восстановление | — | — | Да | Да |
| Ограничить группу / восстановить управление | — | — | — | С причиной |

Platform moderator = Django permission `playergroups.moderate_playergroup`,
не is_staff и не городская роль. Каждая мутация заново проверяет scope и права.
Изменение содержимого требует версии; конфликты не затирают ввод.

## Управление и жизненный цикл аккаунта

Порядок блокировок: затронутые User по pk (`FOR NO KEY UPDATE`) → PlayerGroup по pk → дочерние записи.
Блокировка User допускает FK references; массовое закрытие процессов пишет
audit с process_id, без новой target-ссылки на чужой аккаунт под блокировкой группы.
Одна блокировка группы сериализует join/archive/leave/role/process transitions.
Обычный выход/удаление последнего manager действующей группы запрещён. Для удаления
аккаунта нужна передача или архив. Деактивация по платформенной причине не должна
удерживать аккаунт активным: его групповые роли снимаются, осиротевшая группа
ограничивается и ставится на паузу, восстановление только уполномоченным оператором.
Оператор может предложить руководство действующему участнику или доступному
игроку с действующим scope. Даже в осиротевшей группе membership и роль
появятся только после явного согласия получателя; набор останется на паузе.
Утрата официального scope немедленно прекращает эффективные права; зависимое
участие завершается, старые роли и предложения не воскресают после возврата.
Существующие инварианты городов продолжают действовать независимо.

## Маршруты, контракты и этапы

- `/communities`, `/communities/:slug`: общий каталог и совместимая серверная страница.
- `/groups/new`, `/groups/:slug`, `/groups/:slug/manage`: создание, группа, управление.
- `/account/communities`: приглашения, предложения, текущие связи, заявки и история.
- `/moderation/groups`: отдельные служебные действия с основанием.
- `/api/groups`: typed каталог/detail/create/update, roster и management roster,
  join/leave, заявки, приглашения, руководство, restrictions и audit.
- `/api/account/groups`: личные процессы и связи; безопасный preview приглашения.
- `/api/profiles/public/{username}/groups`: отдельная разрешённая выборка связей.

Этапы локальной реализации: модели/миграции/политики → согласованные переходы и
API → общий каталог и участие → управление и личный кабинет → проверка и demo.
Миграции additive; никаких изменений старых membership, никакой фиктивной истории.
Флаги `player_groups_ui` и `player_groups_write` по умолчанию выключены. Выключение
write оставляет чтение и объясняет паузу действий. Создание доступно активным
аккаунтам с включёнными flags, ограничено настройками; rollout может назначать
write избранным людям. Самостоятельное вступление в официальный Community не
вводится: для него пока нет подтверждённого enrollment-контракта.

Не включаем чаты, ленты, задачи, события, общие invite links, платежи, внешний
notification delivery, синхронизацию Discord/whitelist. Ограничения, consent,
privacy, аудит и последний manager обязательны до включения мутаций.

## Проверка

Нужны тесты полного цикла open/request/invite/leadership, IDOR, ролевых границ,
приватного preview, count, неизменности старой profile privacy, повторов,
archive/pause/version conflict, account/scope lifecycle. Конкурентные проверки
проводятся на PostgreSQL отдельно: SQLite не доказывает блокировки строк.
UI проверяется в текущем E2E, включая 320/390/768/1440, клавиатуру, ошибки и
возврат после входа. Обновление только изолированных локальных demo-контейнеров.
