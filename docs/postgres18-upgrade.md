# PostgreSQL 16 → 18

Новые Compose/Swarm-манифесты используют PostgreSQL 18. Данные теперь лежат
в `/var/lib/postgresql/18/docker`, том монтируется в `/var/lib/postgresql`.
Старый том PostgreSQL 16 автоматически не обновляется. Проверка при запуске
останавливает контейнер с понятной ошибкой, если находит старый `PG_VERSION`.
Не удаляйте том и не запускайте `down -v` для обхода этой проверки.

## Подготовка и область применения

Скрипт `scripts/migrate_postgres18.py` переносит стандартный **локальный Docker
volume** из наших образов `postgres:16-alpine` в новый том PostgreSQL 18.
Он копирует остановленный исходный том с монтированием только для чтения,
запускает копию без сети, сохраняет логический дамп всех баз и ролей, восстанавливает
его в отдельный новый том и сравнивает список баз и количество строк каждой
пользовательской таблицы. Ошибка восстановления останавливает процедуру.
Исходный том остаётся без изменений. Служебная роль initdb остаётся владельцем
системных объектов и сохраняет обязательный атрибут SUPERUSER, но вход и пароль
отключены; членство в этой роли другим пользователям не выдаётся. Пользователи, пароли, права и sequences
включены в полный дамп; интеграционный тест проверяет их сохранение.

До начала нужны:

- проверенная резервная копия и согласованное окно недоступности;
- доступ к Docker на узле, где физически находится исходный том;
- имя существующего superuser (`POSTGRES_USER`, в Swarm — `joutak`);
- место для исходного тома, временной копии, SQL-дампа и нового тома;
- отсутствие внешних tablespaces, внешнего WAL, реплик и нестандартных расширений.
  Для такой конфигурации требуется отдельная процедура.

Дамп содержит пароли ролей и данные пользователей. Скрипт создаёт каталог с
правами `0700` и файлы `0600`. Храните их вне репозитория, с ограниченным доступом.
Скрипт не копирует нестандартные `postgresql.conf`/`pg_hba.conf`: целевой кластер
использует настройки официального образа. Сверьте локальные изменения отдельно.

## Перенос

1. Зафиксируйте старый Git commit, версии образов, имя Compose-проекта/Swarm-стека,
   расположение тома и число реплик сервисов. Остановите приложение, фоновые задачи,
   внешних писателей и затем БД. В Compose используйте `docker compose stop`
   с теми же `-p`/`-f`/`--env-file`, что при обычном запуске. В Swarm сначала
   масштабируйте backend и backend-maintenance до 0, затем db до 0; дождитесь
   остановки задач. Не позволяйте планировщику перезапустить БД до конца переноса.
2. Найдите фактическое имя тома в mounts старого DB-контейнера. Обычно это
   `<project>_postgres_data` или `<stack>_postgres_data`. Не угадывайте имя.
3. Запустите на узле с этим томом (подставьте реальные значения):

   ```sh
   python3 scripts/migrate_postgres18.py \
     --source-volume EXISTING_PG16_VOLUME \
     --target-volume joutak_postgres18_migrated \
     --superuser joutak \
     --backup-dir /secure/backups/joutak-pg18-migration
   ```

   Каталог backup и целевой том должны **не существовать**. Скрипт откажется
   работать с запущенным исходным томом или уже существующим целевым томом.
   Только успешный запуск создаёт `verified.json`. При ошибке дамп и целевой том
   сохраняются для диагностики; не используйте такой том для приложения.

4. Выберите проверенный том через дополнительный манифест. Например, для Compose:

   ```sh
   export POSTGRES_VOLUME_NAME=joutak_postgres18_migrated
   docker compose -f docker-compose.images.yml \
     -f compose.postgres18-migrated.yaml up -d db
   ```

   Используйте своё окружение и прежнее имя проекта. Для dev основной файл —
   `compose.yaml`, для сборки из исходников — `docker-compose.yml`.
   Затем запустите backend/frontend/maintenance тем же набором файлов.
   **Сохраните override и POSTGRES_VOLUME_NAME в постоянной команде деплоя.**
   `external: true` запрещает молча создать пустой том при опечатке.

5. Для Swarm используйте оба `-c`:

   ```sh
   export POSTGRES_VOLUME_NAME=joutak_postgres18_migrated
   docker stack deploy -c docker-compose.stack.yml \
     -c compose.postgres18-migrated.yaml YOUR_EXISTING_STACK
   ```

   До запуска закрепите сервис db за конкретным узлом с целевым локальным томом.
   Одного `node.role == manager` недостаточно в кластере с несколькими manager.
   Внешний том должен существовать именно на выбранном узле.

6. До открытия доступа пользователям проверьте Django migrations, health,
   вход/MFA, профиль, сессии, права доступа и фоновые задачи. Сравнение количества
   строк не заменяет прикладную проверку содержимого. Сохраните дамп и старый том
   до завершения согласованного периода наблюдения.

## Откат

Остановите все новые писатели и PostgreSQL 18. Верните старый Git commit/образы,
старую точку монтирования `/var/lib/postgresql/data` и исходный PG16-том;
уберите `compose.postgres18-migrated.yaml`. Запустите старый стек с прежним именем.
Это возвращает состояние **на момент начала миграции**. Если пользователи уже
писали в новую базу, сначала нужен план сохранения/переноса этих изменений;
простое переключение назад их потеряет. Никогда не запускайте PG16 на PG18-томе.

## Проверка процедуры

```sh
uv sync --locked --group dev --group test
uv run python scripts/check_postgres18_migration.py
```

Тест создаёт только временные контейнеры/тома: переносит Unicode/JSON, несколько
баз, роль с паролем, права SELECT и identity sequence; проверяет неизменность
исходных файлов, отказ для работающей БД и отказ перезаписи целевого тома.
Тот же тест выполняется в CI.

Основание: [официальный образ PostgreSQL](https://hub.docker.com/_/postgres),
[обновление PostgreSQL](https://www.postgresql.org/docs/18/upgrading.html),
[pg_dumpall](https://www.postgresql.org/docs/18/app-pg-dumpall.html).
