# Профиль: предсказуемое редактирование и гостевой вид

21.09.2026. План локальной итерации по двум переданным спецификациям.

Сохраняем Minecraft-ник как основное имя, вторичное имя в профиле, компактные
карточки и правую колонку контактов, baseline 01.01.2026, существующие подписки
и отдельный PlayerGroup. Новых обязательных полей и внешних интеграций нет.

## Решения

1. `CommunityProfile.version` защищает bio/имя/аватар и аудитории. PATCH содержит
   только изменённые поля и обязательную версию. Пропуск — оставить прежнее;
   пустая строка очищает текст; явный null недопустим. Конфликт возвращает 409.
   Старый unversioned публичный редактор получает 422 и должен обновить страницу.
   Это локальный, ещё не выпущенный API; все его consumers обновляются вместе.
2. Контакты имеют отдельный `contacts_version`: редактор списка не конфликтует
   с bio. Ответ API — единственный saved baseline. При 409 введённое остаётся;
   пользователь загружает актуальное и явно сверяет/повторяет правки.
3. `legacy_vk_enabled=True` сохраняет старую аудиторию при миграции. Редактор
   контактов показывает один эффективный VK с прежней аудиторией. После сохранения
   явного набора fallback выключается, даже если VK удалён. Учётный VK остаётся
   в UserProfile для старого account/onboarding процесса.
4. Игровые настройки используют узкий versioned контракт и прежнюю бизнес-
   валидацию account-сервиса. Версия — его `updated_at`, проверенная под блокировкой
   User. Значение передаётся как непрозрачная ISO-строка с полной точностью
   микросекунд: datetime-сериализация Django обрезает её до миллисекунд и не подходит
   для сравнения версий. Старые account endpoints совместимы; их записи также используют этот lock.
   Minecraft-правка не отправляет VK/ИСУ/ФИО. Null и false различаются на чтении.
5. `/account/profile/preview` показывает сохранённое представление реального
   гостя. API принимает только текущего владельца, без username/as_user; вызывает
   те же проекции с viewer=None, включая контакты, связи и группы. Private и
   community профили недоступны в этом просмотре, как и гостю.
6. Собственные подписки получают отдельный список отношений с nullable profile.
   Скрытую цель можно удалить из своих подписок по scoped relation id, не получая
   её актуальных данных. Публичный социальный граф от этого не расширяется.
7. Клиентские обновления scoped по viewer/subject. Черновики не переживают смену
   аккаунта; после game/profile save заново читается разрешённая identity, а не
   подкладывается приватная account schema в публичный профиль.
8. CommunityProfile в Django Admin доступен только для чтения: обход проверки
   версии через обычный admin save недопустим. Контакты и подписки также не
   редактируются напрямую. Аварийные записи через shell требуют отдельного
   операционного решения; это не пользовательский путь редактирования.

## Этап и проверка

Реализуем P0–P1: регрессии перезаписи и VK, редакторы/конфликты, guest preview,
социальные состояния и собственные недоступные отношения. Сначала воспроизводим
выводы чтения кода тестами; существующие корректные политики не переписываем.
Обновляем контракты, миграционные/permission тесты и браузерные сценарии.
Row locking отдельно проверяется на PostgreSQL. Демо только локальное с backup.

Не входят P2: проверка владения Minecraft, реальные серверные события, presence,
репутация, комментарии, блокировки, новые уведомления и production rollout.
